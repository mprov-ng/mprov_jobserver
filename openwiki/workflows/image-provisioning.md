# Image & Repo Provisioning

This is mProv's core pipeline: mirror upstream repos → build a bootable image rootfs from them → pack and serve the image + kernel + initramfs for PXE boot → propagate to other jobservers. All modules here plug in through the [Plugin Framework](../architecture/plugin-framework.md).

## Flow summary

```
upstream repos ──repo-update (dnf reposync)──▶ /export/repos ──served by mprov-webserver──▶ /osrepos/<id>/
                                                     │
                              image-update (dnf --installroot + dracut in chroot)
                                                     ▼
        /export/images/<slug>/ (.img tarball, <slug>.vmlinuz, <slug>.initramfs)
                                                     │  served by mprov-webserver at /images/
                            image-sync / repo-sync pull from peers on version mismatch
```

## Repos: `repo-update` and `repo_update_mod/rhel`

`repo_update.py` claims pending `repo-update` jobs, fetches each `repos/<id>/` from the mPCC, and dispatches on the repo's `ostype.slug` to a submodule found by globbing `repo_update_mod/*.py`. `repo_update_mod/rhel.py` (class `UpdateRepo`) registers the `rhel` ostype with the mPCC (`POST /ostypes/`) on config load, then mirrors with:

```
dnf reposync --repofrompath <id>,"<url>" --repo <id> --destdir=<repoDir>/ \
             --download-metadata [--newest-only] --installroot=<repoDir>/<id>
```

With `newestOnly` the mirror fetches only the newest version of each package instead of the whole history (#95). A repo's own `newest_only` flag in the mPCC wins over the plugin's `newestOnly` default when set; versions already mirrored earlier stay on disk, since `reposync` deletes nothing without `--delete`.

An **unmanaged** repo — `managed: false` in the mPCC, meaning it lives upstream and the mPCC only holds its URL for images to point at — is skipped entirely: the job is marked successful without mirroring, because the alternative pulled whole upstream repos down to every server (#307). A repo payload without a `managed` key at all counts as managed, so an older mPCC doesn't silently disable mirroring.

The `--installroot` trick sidesteps dnf's download lock so repos sync in parallel, and `--destdir` is an absolute path so the plugin never `os.chdir()`s — plugins are threads of one process, and a global chdir would move every other plugin's working directory (#130). On success it PATCHes `repos/<id>/` with only `id` and `hosted_by=[js.id]` — and **fails the job** if the mPCC refuses that PATCH, because a mirrored repo with no host serves nothing (#274). The old `update: False` key that cleared the repo's re-sync flag is gone, because mPCC mprov-ng/mpcc#358 renamed that field to `resync` and clears it when the repo-update job is queued (#204). Upgrade the mPCC first or together: against an older mPCC nothing clears the flag after a mirror, so a later save of the repo queues another sync. Caveat: the mprov-webserver requirement check present in image plugins is commented out here.

`repo-delete` is now implemented (#161): the mPCC queues one paramless "Delete Repos" job whenever a repo is deleted, so on each claimed job the plugin lists `repoDir` (defaulting to `repo-update`'s `repoDir` unless its own is set) and `rmtree`s the mirror directories named purely by a repo id that the mPCC no longer has — anything else in `repoDir` (repo-versions, an operator's files, symlinks) is left alone, since the delete runs as root.

## Images: `image-update` and `image_update_mod/rhel`

`image_update.py` is the orchestrator. On start it hard-requires `mprov-webserver` (source nodes must serve their builds), and it blocks while any `repo-update` job is pending/running because image builds consume the mirrored repos. Per claimed job:

1. Resolve the image's distro/baserepo/extrarepos from the mPCC and dispatch on `osdistro.baserepo.ostype.slug` to `image_update_mod/<ostype>.py`.
2. Post-build steps: first the mPCC's **managed files** (#96, `src/mprov_jobserver/managed_files.py`) — the image entity's `config.files` (merged by the mPCC from distro, groups, and image; each `{slug, name, version, dest_path, owner, group, mode, template, url}`) are downloaded (≤10 MiB) and placed into the rootfs **after the base OS and before the image-gen scripts**, so scripts and Ansible can use them. Templates are the copies the mPCC rendered for this image (read with the job server's certificate, see [Identity and Certificate Enrollment](../architecture/identity.md)); anything else is the uploaded file under `/media`. Every entry is validated before anything is written — absolute normalised destination outside `/proc`, `/sys`, `/dev`, `/run`, `/tmp/mprov`, no symlink in any existing path component, mode 3–4 octal digits with setuid/setgid refused unless `allowSetuidFiles` is on, owner/group as names or numeric ids (resolved inside the image via `chroot <img> chown`) — and any problem fails the build so nothing half-configured is packed. What was placed is recorded in `/var/lib/mprov/placed-files.json` in the image; a file no longer attached is removed at the next build. If the path belonged to a package before placement, the placed copy is **always removed first** and the package reinstalled, with the result checked against the digest rpm records for the path rather than the reinstall's exit code — rpm leaves an existing `%config(noreplace)` file alone on a same-version reinstall and still succeeds, so the managed content (secrets included) could survive a "restored" log line (#348). A package that can't restore the file fails the build (the placed copy is already gone) and the manifest keeps the entry so the next build retries; a `%ghost` path isn't expected back. The log names each file and its version, never its contents (a rendered template holds the image's Configuration Parameters). Then: copy `resolv.conf`, then put the job server into the image as a **portable Python bundle** instead of pip-installing it (#309): `installBundle()` unpacks `mprov-jobserver-<version>-x86_64.tar.gz` — a self-contained Python 3.11 with the job server and its dependencies — at `/usr/libexec/mprov` and symlinks `/usr/local/bin/mprov_jobserver` into it. The bundle's `MPROV_BUNDLE_VERSION` marker must equal the building job server's version (stricter than the old API-version pip pin, #303), its paths are realpath-checked to stay inside the image tree (`inside()`, #169), extraction uses tarfile's `tar` filter, and the new tree swaps in via a `.new`/`.old` rename so a failure leaves any old bundle in place. The container image carries the bundle in `/usr/share/mprov/`; a pip-installed job server has none and must set `pythonBundle:` to a bundle downloaded from the GitHub release, or builds fail with a message saying so. `removePipInstall()` first uninstalls a 0.6-era pip-installed copy from a rebuilt image (best effort, bounded by `pipUninstallTimeout` 300s); `pipTimeout` is kept only so old configs don't log an unknown-setting error. Then inject distro root SSH keys and password — the keys land in the **image tree** (`<imgDir>/root/.ssh/authorized_keys`, 0700/0600), never on the build host (#175), and the password reaches `chroot <imgDir> chpasswd` only over the subprocess's stdin pipe (chpasswd is non-interactive, and the job fails if the password doesn't take, #229), redacted in debug prints, never placed in a shell command line or argv where `/proc` would expose it (#168) — run image-gen scripts by rendering `templates/image-update/script-runner.sh` and chrooting a runonce jobserver (see [Script Execution](../workflows/script-execution.md)); the run is bounded by `scriptTimeout` (default 7200s, 0 = no limit) via `runBounded()`, which on timeout SIGTERMs the runner's whole process group — a shell alone would defer the signal while the actually-stuck child carries on — and SIGKILLs it after `killGrace` (30s); since SIGKILL runs no traps, the build then unmounts the host's dev/proc/run/sys binds itself via `unmountStaleBinds(imgDir)` (#304). The wrapper now preserves the chrooted jobserver's exit code, so a failed image-gen script fails the job and no image is packed (#221). The runonce config the build writes under the image (`<imgDir>/tmp/mprov/jobserver.yaml`) is 0700 in a directory owned by the build uid (refused otherwise), created `O_NOFOLLOW` at 0600 and unlinked after the scripts run (#169). What it holds depends on how the job server authenticates (#336): on the shared API key it holds the **fleet API key** (as before); a job server with its own certificate instead requests a **2-hour build credential** that can only read this image (`POST enroll/build/`, see [Identity and Certificate Enrollment](../architecture/identity.md)), saves it in the image's `/tmp/mprov/tls`, and drops `apikey`, `enrollToken`, `enrollTokenFile`, `caFingerprint`, and `nodeTlsDir` from that config, setting `tlsDir` to `/tmp/mprov/tls` — so no long-lived secret is baked into any image. The build fails if the credential can't be obtained, and a final guard refuses to pack the image while `/tmp/mprov/tls` still exists (the credential is removed with a never-follow-links `remove_build_credential()`). Then fetch a static busybox into a 0700 root-only `<imageDir>/.busybox` and refuse to run it unless the download starts with the ELF magic — a fixed world-writable `/tmp` path let another user plant a binary for the root daemon (#170) — call the submodule's `updateBootFiles()` if present (its failure fails the job and skips packing, #144), then pack the rootfs: `busybox tar | gzip -1` into a temp file `os.replace`d over `<slug>.img` only once tar and gzip both succeed, so a failed pack can never destroy the previous image (#216, #232).
3. On success only, register itself as the image's host through the shared `patchAsHost()` helper — the same one `addAsHost()` uses on the heartbeat pre-pass — and bump the local `image-versions` JSON tracker in `imageDir`. A registration the mPCC refuses (other than 409) is logged with its reason, and the build still succeeds: the image is built/published and `image-versions` records the version, so the next `updateImageJobservers()` pass registers it (#352). A 409 (the image moved version-wise while being built) still tears down what was published and fails the job.

Every error path in the per-image loop fails **only that job** — `update_job_status(..., status=3, jobid=jid)` — and `continue`s to the next image (#143, #144, #220); a module import failure, a chroot pip failure, a failed image-gen script, a bad busybox download, or a failed pack never stop the other images' builds. Jobs are claimed per configured image via `jobs/?module=image-update&params=<{"imageId":...}>` — the mPCC matches `params` key by key, and pending jobs have no jobserver yet so the claim can't filter on it (#172, #144).

`image_update_mod/rhel.py` (class `UpdateImage`) builds the RHEL-family rootfs — **a directory chroot, not kickstart**:

- **Base image path (#92)**: if the mPCC's distro has a `base_image_url`, `plugins/base_image.py` downloads it (SHA256-verified against `base_image_checksum`, BSD/GNU checksum formats or a bare digest), detects its format **from the file contents, not the URL** (`detect_format()` — OCI archive or rootfs tarball, or since 0.7.0 a cloud disk image: qcow2 or raw, optionally xz-compressed or the sole member of a tarball, as Debian ships them). Disk images are read with libguestfs (`guestfish -i tar-out`), which runs in its own small VM so the host never mounts the image's filesystems; the appliance is cached in `/var/lib/mprov/guestfs` (a container volume, so it survives restarts) and emulation is used without `/dev/kvm` (slow — the container installs `guestfs-tools`, a pip-installed job server needs the host to have it). It then unmasks the systemd units container base images mask, runs `clean_unpacked()` to drop what a cloud disk carries that belongs to its install machine (grub config and boot loader entries, rescue kernel, hostname, SSH host keys), and records an `/etc/mprov-base-image` marker so a changed base is noticed next build. `strip_base_image()` then removes what a cloud base must not carry into a bare-metal image (cloud-init, the base's own kernel), and the distro packages install on top. Without `base_image_url` the bootstrap below runs as before.
- Writes `mprov`-managed `.repo` files pointing at `{mprovURL}/osrepos/<id>/` (gpgcheck=0), disables stock repos (baseos/appstream/epel/extras/powertools/crb). Before any chroot `dnf` runs — including the first package install — the image gets a copy of the host's `/etc/resolv.conf`, or glibc resolves repo hostnames against `127.0.0.1` and the first build fails on a host whose resolver is loopback-only (#281).
- `dnf --installroot=<imgDir> groupinstall 'Minimal Install'` with a fallback that retries via `chroot imgDir dnf ...`; installs a fixed package set (kernel, grub2 + EFI modules, mdadm, ipmitool, parted runtime lib, `python3` packages only on EL9 — since #309 EL8 images no longer get python38 or the pip packages, because the job server and node scripts run on the bundled Python) and freezes the kernel with `dnf versionlock kernel*`. Retries once after `rpm --rebuilddb` on failure. Before the first in-image install, `convert_host_rpmdb()` rebuilds a new **EL8** image's rpm database: the Rocky 9 job server's rpm creates it as sqlite during the host-side `--installroot` passes, which EL8's rpm cannot read, so an EL8 image would otherwise hit alarming `--rebuilddb` errors on its first chroot install (#329). An image without `rpmdb.sqlite` (an EL8 job server's bdb database, or a rebuild of an existing image) is left alone.
- Symlinks newest non-rescue kernel/initramfs out as `<slug>.vmlinuz` / `<slug>.initramfs`, `mknod`s `/dev/ram0`+`/dev/initrd`, and regenerates initramfs with `dracut --regenerate-all -f --mdadmconf --force-add mdraid --add-drivers sd_mod ...` (repeated in `updateBootFiles()` after scripts run, so the final initramfs includes script changes). The distro's `initial_mods` list is first filtered by `realModules()`, which keeps only names that `modinfo -k` confirms as modules of every kernel in the image: dracut-install stops at a built-in or unknown module and silently drops every driver listed after it (#206).
- No subscription-manager flow exists; everything is `--nogpgcheck` plus mProv-generated repo files.
- When a global `caBundle` is configured, `mpcc_ca()` copies the mPCC's CA into the image twice — at the same absolute path (the host's dnf reads `sslcacert` from the image's repo files as a *host* path during the install passes) and into `/etc/pki/ca-trust/source/anchors/mprov-mpcc.pem` — then runs `chroot <img> update-ca-trust` before packing, so the chroot's dnf and the booted nodes trust a site/self-signed mPCC too (#267).

Caveats: heavy `os.system` string interpolation and chroot of the half-built image are by design (root daemon, trusted mPCC input).

## Serving: `mprov-webserver`

`mprov_webserver.py` is a `ThreadingHTTPServer` (default port 8080, `rootDir: /export/`) that serves repos at `/osrepos/...` and images at `/images/...` for PXE downloads and peer pulls. Three guards protect it:

- **Root safety (#214)**: `safe_root()` refuses to start (or to accept a request) when `rootDir` is empty, `/`, or not a directory — an empty `rootDir` means the working directory, which is `/` under systemd, so the whole filesystem would be exposed. The server passes its root into each handler so the fallback never applies.
- **Load shedding**: `/images/*` GETs are refused with 404 when the **5-minute** load average (`os.getloadavg()[1]`) ≥ CPU count and `loadmon` is enabled, reading load and the job server handle from the server object, not the handler (#147). The 404 makes clients retry another jobserver — the mPCC HEADs each server before redirecting and skips one that refuses — while the daemon keeps heartbeating so a busy server is never deleted from the mPCC (#148, see [Architecture Overview](../architecture/overview.md)).
- **Connection limit (#148, #185)**: the `maxConn` (10) counter applies only to *image* GETs whose file is ≥ `maxConnFileSize` (default 0 = every image file); the path is classified via `translate_path` so `//images/` and `/x/../images/` count too, the file is stat'd without holding a descriptor, and non-image or missing files go straight to `SimpleHTTPRequestHandler`. HEAD never takes a slot (it's the mPCC's per-redirect probe), and slots are released in a `finally` so aborted downloads don't leak.

Caveat: `maxConn` remains a hardcoded class attribute (TODO in source); it is now live code on the image path, not dead.

**Provisioning metric (#105)**: every image GET or refusal logs one line to a separate `provisioning` logger — `node (ip) requested/turned away from image <slug>` — so a time-to-provision metric can be built from the boot-file requests the webserver already sees.

## Propagation & teardown: `image-sync`, `repo-sync`, `image-delete`

- `image-sync` (requires `mprov-webserver`) runs every heartbeat, not job-driven: compares each image's mPCC `version` against a local `image-versions` JSON file, downloads `.img`/`.initramfs`/`.vmlinuz` from a peer when they differ, registers itself with `?addjs`, and sweeps directories under `imageDir` not in the configured list. Its `?addjs` PATCH carries only `slug` + `jobservers` — it deliberately omits `needs_rebuild`, because sending `False` cleared a rebuild the operator asked for since the plugin's GET (#226). `repo-sync` mirrors the same pattern with `wget --mirror` into `repoDir` (note: no `repo-sync.yaml` ships, so it runs on empty defaults unless configured inline).
- `image-update`'s heartbeat pre-pass (`updateImageJobservers`) participates in the same pull pattern: for configured images it doesn't yet host and whose version differs, it pulls from a peer **through the mPCC redirect** via `image_update.py::pullImage` — each artifact downloads to a dotfile temp and is `os.replace`d into place only once all three succeed, so a failed pull (e.g. every host full and answering 404) keeps the previous image; on success it records the version and adds itself as host (#142). It skips images with `customIPXE` set or `needs_rebuild` requested.
- **Sweep safety (`dataRoot` + `.mprov-managed` marker, #171)**: because the sweep `rmtree`s unlisted directories, both sync plugins refuse to load (`sys.exit(1)` in `load_config`) unless the configured `imageDir`/`repoDir` sits inside a declared `dataRoot` (helpers `path_is_under`/`mark_mprov_dir`/`is_mprov_marked_dir` in `plugins/plugin.py`, realpath-checked so symlinks or `..` can't escape). Each directory a sync plugin creates gets a `.mprov-managed` marker file, and the sweep deletes only marked directories — unowned directories are logged and left alone, so a mistyped sync directory can never wipe operator data.
- `image-delete` (config `image-delete.yaml`) is job-driven: claims `image-delete` jobs scoped to this server and deletes `imageDir/<imageId>` directories it hosts. It shares the `imageDir`/`image-versions` convention with image-update but does not prune the versions file.

The mPCC `jobservers`/`hosted_by` lists plus the `?addjs` PATCH convention are how the control plane knows which server can serve which artifact — all image/repo modules participate in this **self-registration dance**. An `?addjs` PATCH carries only the keys a job server's certificate may send there — `slug`, `jobservers`, `version` — since the mPCC refuses (403) any other key, which is why the build's old `needs_rebuild: False` lost its registration (#352); `image_update.py` now funnels both the build and the pre-pass through one `patchAsHost()` that logs such refusals. It carries only our own id (never a list read from a possibly-stale GET, which could drop other hosts, #248) and, when the mPCC advertises the `addjs-version` feature, our local image `version` — a 409 means the image has moved past us, so the plugin fetches the mPCC's fresh version onto the image instead of silently claiming hosting (#248, part 2; `addjs_version()` in `plugins/plugin.py`).

## Ad-hoc tooling

`repack_image` (repo root) re-packs an unpacked image directory with the same busybox-tar pipeline for manual fixes. It parks the existing `.img` outside the tarred directory and swaps the new one in with a same-filesystem `mv` only after tar+gzip succeed, restoring the parked image on any failure — a failed repack can never destroy the image it repacks (busybox tar has no `--exclude`).
