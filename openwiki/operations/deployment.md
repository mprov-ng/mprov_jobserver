# Operations & Deployment

## Supported deployment: container

The job server runs as a container; **bare-metal install is no longer supported or documented** (#300). `install_mprov_jobserver.sh` and the systemd unit files (`src/mprov_jobserver/systemd/`) are still in the repo, but nothing here documents or tests running the job server as a system service. The PyPI package stays published because `image-update` puts a job server into every built image — since 0.7.0 as the portable Python bundle rather than a pip install (#309) — so nodes get `script-runner` and `MProvScript` (see [Script Execution](../workflows/script-execution.md)). From 0.7.0 the package requires **Python ≥ 3.11** (`setup.cfg`, #311), enforced by the `mprov_jobserver` launcher; node images need no particular Python of their own for the job server, which carries its own.

Runtime dependencies are in `requirements.txt` (pyyaml, jinja2, requests, python-slugify, py-dmidecode, netifaces, pyparted, sh, pyroute2 0.8.1, dnspython, distro, psutil, cryptography ≥ 42 for the job server's key and certificate, #381). Packaging metadata: `setup.cfg` / `setup.py`; package data ships all plugin YAMLs and `templates/*/*`.

First run of the `mprov_jobserver` binary with no `/etc/mprov/jobserver.yaml` copies template configs into `/etc/mprov/` and exits for editing (see [Architecture Overview](../architecture/overview.md)) — in the container this doesn't apply, since the entrypoint always renders the config from the environment.

## Container image

`Dockerfile` / `Containerfile` (identical), on **Rocky Linux 9** since #111 (its dnf/rpm build the node images and sync repos, and an EL8 rpm can't read an EL9 image's sqlite rpm database), with EPEL + CRB + Development Tools, dnsmasq/ipmitool/tcpdump/iproute, and `guestfs-tools` (with weak deps off) for reading qcow2/raw base images — the libguestfs appliance is cached in `/var/lib/mprov/guestfs`, which the compose stack puts on the host. Exposes `69/udp` (TFTP), `67/udp` (DHCP), `53/udp` (DNS), `8080/tcp` (webserver) — matching the dnsmasq and mprov-webserver plugins in [Network Services](../workflows/network-services.md) and [Image & Repo Provisioning](../workflows/image-provisioning.md).

**The job server runs on its own Python, not the OS's (#309, #111).** A separate `bundle` stage (kept on EL8 whatever the final image is, so the compiled extensions pyparted/netifaces only need EL8's glibc and run on EL8 *and* EL9 nodes) downloads a pinned python-build-standalone CPython (versions + SHA256 in `container/python-bundle.lock`), installs the job server into it with `container/install_jobserver.sh`, smoke-imports everything the job server and baked node scripts need, stamps `MPROV_BUNDLE_VERSION`, and tars it as `mprov-jobserver-<version>-x86_64.tar.gz`. The main image unpacks that tarball at `/usr/libexec/mprov`, keeps the tarball in `/usr/share/mprov/` for `image-update` to unpack into node images, and symlinks `/usr/local/bin/mprov_jobserver` into the bundle; EL9's platform Python exists only for dnf. A `bundle-export` stage emits just the tarball so `ci_build.yml` can attach it to the GitHub release — a pip-installed job server downloads it and points `pythonBundle:` at it (see [Image & Repo Provisioning](../workflows/image-provisioning.md)). The launcher (`src/mprov_jobserver/mprov_jobserver`) prefers the interpreter **next to the resolved symlink target** (`readlink -f` first — in a node image the launcher is a link into the bundle, #310) and dies below Python 3.11 (#311). `install_jobserver.sh` (used by both stages, pinned by `container/requirements.txt`) fails the build when `dist/` holds more than one wheel (#322) and says plainly when it falls back to the PyPI release instead of the checked-out code (#320).

**Env-var config templating**: the image ships `jobserver.yaml.j2`; `start_server.sh` first runs `mprov_jobserver.container_config` (#334, below), then sources `/etc/mprov/apikey` if present (a legacy fallback the mPCC container may still write), renders the template with inline Jinja over env vars, and execs the job server. Variables: `MPROV_URL` (from 0.7.0 must be `https://`, since the job server authenticates with its own certificate — see [Identity and Certificate Enrollment](../architecture/identity.md)), `MPROV_ENROLL_TOKEN`, `MPROV_CA_FINGERPRINT`, `MPROV_TLS_DIR` (default `/var/lib/mprov/tls` — keep it on storage that survives container recreation), `MPROV_ADDRESS`, `MPROV_MODS` (space-separated module list), `MPROV_ARGS` (extra CLI args), `MPROV_APIKEY` (deprecated shared-key fallback, only written when set), `MPROV_CA_BUNDLE` and `MPROV_LOG_LEVEL` (optional, written into `global:` only when set, #301), `TZ`, and the dev-only `MPROV_SKIP_VERSION_CHECK` (see [Architecture Overview](../architecture/overview.md)). Because the file is regenerated on every start, per-module settings belong in `/etc/mprov/plugins/` on the config volume — and since #301 a plugin file there can also carry a small `global:` section (e.g. `hostId`, `logTimestamps`), which merges into the rendered globals instead of replacing them (see [Architecture Overview](../architecture/overview.md)); a complete config of your own via `MPROV_ARGS=-c` still works but is no longer needed. The `ENTRYPOINT` is exec-form `/start_server.sh` (no shell-expanded argument — `"${MPROV_ARGS}"` used to reach the launcher as a literal string), and both `start_server.sh` and the `mprov_jobserver` launcher `exec` the job server so a container SIGTERM reaches it instead of orphaning it (#294). The dead `mprov_jobserver.conf` systemd drop-in was dropped from the image — the unit it configured isn't installed there (#295).

**Shipped-config refresh (#334)**: `/etc/mprov` is a volume shared with the mPCC (mprov-compose's `mprov-conf`), and Docker only seeds a volume while it's empty — so a job server created after the mPCC wrote its secrets never got the template, and upgrades never delivered new template/plugin defaults. The image keeps a pristine copy of its config under `/usr/share/mprov/config` (with `shipped-config.sha256` listing every hash each shipped file has had), and `start_server.sh` runs `python -m mprov_jobserver.container_config` on **every start** before rendering: a shipped file that's missing is installed; one identical to a version an earlier release shipped (i.e. unedited) is replaced; a site-edited plugin config is kept and the new default written beside it as `<name>.yaml.new` (which the `!include plugins/*.yaml` glob doesn't pick up) until the site file matches the default again; an edited `jobserver.yaml.j2` is replaced with the site copy kept as `.bak`. Stale plugin `*.py`/`__pycache__`/`*_mod/` code that earlier images copied into `/etc/mprov/plugins` is removed (plugins are imported from the installed package only). The mPCC's secrets, the rendered `jobserver.yaml`, and site files (a CA bundle, `local.yaml`) are untouched, and a failure is logged but never stops the start.

## Dev stack

`dev-docker-compose.yml` runs the dev image with `network_mode: host`, `privileged: true`, systemd init, volumes for `/etc/mprov` config and `/export` (images/repos/tftpboot persistence — `/tftpboot` was deliberately moved under `/export/tftpboot` for persistence), env from `stack.env` (copied from `stack.env.example`; git ignores `stack.env`), and `wait-for-it.sh` gating on the local mPCC at `localhost:80`.

## CI

`.github/workflows/`: `ci_build.yml` (build/publish), `dockerimage-dev.yml` (dev container image → `ghcr.io/mprov-ng/mprov-jobserver`, versioned `X.Y.Z.devN` from `VERSION` on pushes to main, with concurrency so only the newest push publishes, #247), `lint.yml` (ruff errors-only + ShellCheck on every PR/push, independent of the image build, #187), `update_website.yml`, and `openwiki-update.yml` (this documentation). Pull requests run the dev/release workflows as dry runs that stop after the tests; `.github/dependabot.yml` keeps Actions deps current. The **pytest suite in `tests/`** runs inside the just-built jobserver image via `tests/Dockerfile` (adds pytest + `genders` for `nodeattr` checks), so tests use the same Rocky build, Python, and dnsmasq that ship. `gen_changelog.sh` generates release notes from git history; `VERSION` is the source of truth for releases.

## Operational checklists

- **Changing plugin config keys**: update both the plugin class default and its YAML in `src/mprov_jobserver/plugins/`; existing `/etc/mprov/plugins/*.yaml` on deployed hosts are not auto-migrated.
- **New Python dependency**: add to `requirements.txt` *and* the Dockerfile install line if it has system build deps (e.g. pyparted needs parted-devel).
- **Container**: any new listening port needs an `EXPOSE` update; anything stateful belongs under `/export` or the `mprov-conf` volume.
- **Changing plugin logic**: add or update a pytest case in `tests/` (the fixtures in `tests/conftest.py` serve canned mPCC responses and stub out host side effects); CI runs the suite in the shipped image. For live smoke-testing use `-r -d -m <module> -c <config>` against a dev mPCC.
